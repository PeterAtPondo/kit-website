The existing rgba(var(--kit-NAME), alpha) idiom stays exactly as it is for primitives (index.html:141-144); the semantic layer sits beside it, it does not replace it.

1.2 Colour: how the two forms meet
  • A primitive is a triplet; it is never used on its own as a value. Opaque use is rgb(var(--kit-amber)), tinted use is rgba(var(--kit-amber), var(--kit-soft)).
  • A semantic colour token is a resolved colour and is used as a value: color: var(--kit-text-primary), background: var(--kit-surface-raised).
  • Where a role must also be tinted (accents, states, the light colours) the token carries an -rgb twin that is the triplet: --kit-accent-primary-rgb: var(--kit-amber), so rgba(var(--kit-accent-primary-rgb), var(--kit-soft)) composes without reaching back to the primitive. Ink has no twin on purpose: ink is never tinted with alpha, the ink step is chosen instead (colour section 1.8).
  • Alpha always comes from the six named steps (--kit-tint .06, --kit-faint .10, --kit-soft .18, --kit-fill .40, --kit-strong .60, --kit-solid .92, index.html:169-174). No new steps; no raw .45, .35, .62, .78.
  • A var() inside a custom property resolves where that property is declared. Semantic tokens are declared on :root, so overriding a primitive on a subtree does nothing to the semantic tokens above it: override the semantic token itself (this is how the light context block works). The one composed token that reads a per-element parameter, --kit-shadow-halo, is therefore declared on *, not on :root (section 2.16).
1.3 Rules for consumers
  1. Components and utilities reference semantic tokens. Primitives appear only inside the token block, in data encodings, and in the runtime mood map (main.js:12663-12775), which already composes from triplets.
  2. No raw hex, no raw rgba(r,g,b,a), no stock Tailwind colour utility outside the remapped amber scale and the slate family used for data. The audit counted 70 distinct hex literals in index.html, about 60 in partials, 116 in main.js (audit/AUDIT.md section 3, counts); each maps to a row below.
  3. A token changes in one place: tokens-semantic.json is the source, tokens.css, the Tailwind map, the widget string and the Lantern copy are generated from it (section 5).
  4. Names describe the job, not the number, the same way the alpha scale already does (index.html:164-168): --kit-motion-reveal, not --kit-t-3; --kit-hit-touch, not --kit-44. Space and radius keep ordinal names because the guide fixed them that way (--kit-space-1 to --kit-space-10, --kit-radius-1 to --kit-radius-4 plus pill).
  5. Export-only values (the tile gradient, its three stops and the 22 percent corner, the meta theme colour, the firefly field constants in rad/s) live in the JSON with css: false and never enter the product stylesheet, because the tile never appears inside a Kit surface (colour section 3.5).

The scenes

the four long waits, one field, four moods · live mocks · every firefly is data

Data, not decoration. The field is never random when there is something real to show. In the wake it is this Kit's last fourteen days, one firefly per forty memories, a column per day, lavender where a dream ran, the brightest of each day threaded to the next. The updater shows the same fortnight, because nothing about the memory changes while Kit updates. Dreaming shows tonight's consolidation batch grouped by what is being merged, the traces are the links being made. An import shows each batch landing and threading to its nearest neighbour. When there is truly no data (a brand-new Kit), the field is sparse and says so.

Colour means something. Each firefly carries the hue of its memory's project or source, the same palette the galaxy uses (Kit lavender, Northwind teal, Acme plugins amber, Whiskerwool orange, people rose, Ridgeline Wealth blue), and the city-light rule keeps every core near white and puts the colour in the halo, so the field reads as light rather than paint. With no data it is amber. While dreaming the whole field is tinted lavender, the state colour, over the data hues. A chip, a dot, a label and a firefly for the same thing are always the same colour.

Depth. Three planes. Far: small, soft, slow, 45 percent of the fireflies. Mid: sharp, the ones that carry the data. Near: large, soft, half transparent, a few, drifting fastest, the bokeh of a light close to the lens. Size follows the language's long tail, brightness is independent of size, every firefly has the galaxy sprite's oval and lobed rim, and the traces are bowed, two passes, with sprite dots along them.

5.3 How to build it in AppKit

The hard part is that a template image is tinted whole by macOS, so a coloured pip inside a template image would be tinted too (which is exactly why :1026 turned templating off). Two ways that keep both:

  1. Recommended. A drawing-handler image, NSImage(size: 22x22, flipped: false) { rect in ... }, isTemplate = false. Inside the handler: draw kit-menubar-template (loaded from Resources/, isTemplate = true) and tint it with NSColor.labelColor using sourceAtop; clear the pip ring with destinationOut; fill the pip with KitTokens.Color.<state>. AppKit re-runs the handler whenever the appearance or backing scale changes, and labelColor resolves per appearance, so light and dark bars both work without observing effectiveAppearance. Known trade: the glyph does not invert while the menu is open the way a true template does. Accept for v1.
  2. Alternative. button.image is the template glyph (true template, inverts on highlight) and the pip is a 6 by 6 pt NSView subview pinned to the button's bottom-right, drawing the disc and the knockout. Cleaner behaviour, one more view to keep aligned. The library can pick; the spec above holds for both.

Either way kitMenuBarGlyphImage (Swift:1080-1112) stops drawing geometry: the geometry comes from the shipped template (Resources/kit-menubar-template.pdf or the 22 and 44 px PNGs), so the menu bar shows the same mark as everywhere else (AUDIT.md inconsistency 5).
